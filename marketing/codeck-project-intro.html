00 / 先说人话

30 秒看懂 Codeck

先抓住一件事：Codeck 自己不会思考，也不提供模型。它负责让不同 AI 接手同一个项目时，不必从零开始。

它是什么

一个运行在你电脑上的“AI 项目交接员”。

它解决什么

换一个 AI 帮忙时，项目背景、当前改动和开发规则会断掉。

它怎么解决

自动收集必要信息，按你的指令送给指定 AI，再把过程和答案留在项目里。

谁最适合用

以 Codex 为主力，但偶尔需要另一个模型做审查、分析、对比或专项工作的开发者。

一句话：Codeck 不是新大脑，而是让几个大脑顺利接班的交接台。

01 / 项目背景

为什么会需要这个项目？

不同 AI 各有所长，但它们不会自动共享记忆。真正折磨人的，常常不是“没有好模型”，而是“每换一次模型都要重新交代一遍”。

以前：你自己当搬运工

  1. 从 Codex 切到另一个终端。
  2. 复制项目介绍、目录和开发规范。
  3. 再复制当前改到一半的代码差异。
  4. 担心复制少了它看不懂，复制多了又慢又贵。
  5. 拿到答案后，再手工搬回 Codex。

现在：Codeck 做交接

  1. 你明确说：“让 Agy 看一下当前改动。”
  2. Codeck 按规则挑出这次真正需要的项目材料。
  3. 外援收到任务、背景、规则和当前改动。
  4. 答案回到当前工作流，运行过程也有记录。
  5. 你仍然是决定找谁、采纳什么的人。

02 / 核心问题

它真正要补的是“信息断层”

模型之间没有共同记忆。一次看似简单的“换个人看看”，背后至少有四个实际问题。

新来的 AI 不知道项目发生过什么

它看不到你刚才的对话，也不知道项目架构、分支状态、改了哪些文件，更不知道哪些规则绝对不能碰。

人工复制上下文又慢又容易漏

漏一条约束，答案可能跑偏；整仓库都塞进去，又会拖慢速度、增加费用，甚至超过模型能一次读完的长度。

“可以看”与“可以改”容易混在一起

做代码审查通常只需要读取；真正改文件则需要更高权限。没有清楚边界，外援可能做得太多。

答案散落在不同工具里，之后找不到

哪个模型说过什么、当时看到的是哪版代码、为什么做这个决定，过几天往往就说不清了。

把它想成一个施工项目

决定目标、预算，以及最后听谁的。

一直留在主现场，负责把工作真正收口。

整理资料、按你的点名送达、带回意见，并把交接单留档。

03 / 解决方案

Codeck 用四件事把断层补上

它不试图替代现有 AI，而是在它们中间补一层稳定的交接流程。

01

自动整理“上下文行李箱”

把这次任务、项目说明、开发规则、Git 状态、未提交改动和相关文件组合成一份有结构的文字材料。

任务READMEGit diffAGENTS 规则相关源码
02

控制行李箱大小

快速问答默认只带较小上下文；复杂任务可用完整额度。内容太多时，先拿掉低优先级材料，必要时再截短，避免一次塞爆。

快速问答：约 16,000 字符完整任务：约 60,000 字符
03

把同一份任务翻译给不同工具

Claude、Kimi、Grok、Agy 和 API 的启动方式不同。适配器会把统一交接单变成每个工具听得懂的命令，所以路由层不用为每家重写一遍。

本地 CLI直连 API通用命令适配
04

把交接过程留在项目里

任务、当时的上下文、过程输出和最终答案会进入项目本地归档。之后可以搜索、收藏、回放或导出，不必靠记忆找结论。

搜索收藏回放导出明显密钥默认掩码

04 / 完整流程

一句话发出后，里面发生了什么？

下面是从你开口，到答案回来的真实主链路。

  1. 01

    你提出明确任务

    例如：“让 Grok 只读检查当前 diff，按风险排序。”任务不能为空，也要说清楚要谁做什么。

  2. 02

    Codeck 检查该执行者能不能做

    它确认执行者存在、当前模式允许、权限合适。MCP 入口不会自动启动可写文件或可跑命令的高权限执行者。

  3. 03

    收集这次需要的项目材料

    任务、项目说明、约束、分支、最近提交、Git 状态、当前差异、README、规则文件和被点名的源码被整理在一起。

  4. 04

    按预算删减并生成交接单

    重要信息优先保留；次要材料超出长度时会被省略或截短。交接单最后是一份结构化 Markdown，也就是容易阅读的纯文本。

  5. 05

    通过对应 CLI 或 API 发给外部模型

    适配器使用该工具需要的参数启动进程，或调用它的网络接口。这里是数据真正离开 Codeck 本地整理区的地方。

  6. 06

    边运行，边记录

    输出会逐步保存。若 MCP 等了接近 45 秒还没完成，先返回一个 runId（运行编号）；任务继续跑，之后用 wait_run 取结果。

  7. 07

    答案回来，Codex 继续主持

    Codeck 返回结果与使用量；Codex 和你负责判断哪些建议可信、是否落地。归档保留这次交接的来龙去脉。

最重要的分界线在第 5 步：整理和归档默认在本地，但送给外援的内容会到达那个模型的服务商。

05 / 使用方式

不同命令，代表不同授权

先预览、只咨询、授权实施、多人对比，是四件不同的事。Codeck 把它们分开，避免“只是问问”变成“直接动手”。

手机上可左右滑动查看完整表格。

命令大白话会不会调用外援典型用途
pick先看看这活准备交给谁不会预览路由，避免叫错人
ask请外援只给意见会分析、审查、解释、第二意见
delegate明确授权外援实施会写文件或运行命令；高权限执行者在命令行需要确认
compare同一道题交给多个外援会，多次找共识、看分歧、比较方案
wait继续等上次没跑完的活不会新开任务用 runId 取回长任务结果
replay拿旧交接单再跑一次会，新建一次运行复现旧分析，或与当前项目状态对照

06 / 代码结构

如果打开源码，该从哪里看？

项目是一个 Node.js + TypeScript 命令行工具，同时提供 MCP（让 Codex 调本地工具的接口）。核心文件各管一件事。

src / 项目主干地图
index.ts命令行总入口：把 init、ask、compare、wait、replay 等命令接到真正逻辑上。
mcp.tsCodex 接口：把 Codeck 的能力暴露成可以在对话里调用的本地工具。
config.ts规则本：默认执行者、关键词、权限、上下文长度、归档选项都在这里。
context.ts行李箱打包员：读取任务、Git、README、规则和相关文件，并负责删减。
router.ts调度中心：选执行者、检查权限、启动任务、等待、取消、对比和交接。
adapters.ts翻译器：把统一任务转换成 Claude、Kimi、Grok、Agy、Codex 或 API 各自需要的调用方式。
archive.ts档案柜：本地保存、掩码明显密钥、搜索、收藏、回放、导出和删除。
models.ts共同表格：规定任务、执行者、上下文和运行记录都长什么样。

07 / 权限与数据边界

它很有用，但不是魔法保险箱

这部分最容易被宣传语带过去，也最值得先看懂。

它已经做的保护

  • 在 Codex 的默认使用约定里，只有你明确点名外援才交接。
  • pick 可以先看路由结果，不发出请求。
  • MCP 不会自动运行可写文件或可执行命令的高权限配置。
  • 本地归档默认掩码常见 API Key、Token 和私钥样式。
  • 归档文件使用收紧的本地文件权限，超长内容另存到受控目录。

它不能替你保证的事

  • 它不提供模型账号、订阅、额度或网络可用性。
  • 一旦明确发送，选中的项目内容会进入外部模型服务。
  • “只读”配置首先是一份权限声明；是否硬隔离，还要看底层 CLI 有没有真正的沙箱。
  • 自动掩码只能抓常见秘密，不能保证发现所有敏感信息。
  • 外部模型给出的建议仍可能出错，最后必须由 Codex、测试和人来验证。

最稳妥的第一次使用

先在不含敏感资料的小项目里跑一次只读 ask。检查行李箱带了什么、外部 CLI 登录是否正常、结果是否能顺利回来，再决定要不要扩大范围。

08 / 最短上手路径

第一次跑通，只要三步

前提：Node.js 20 或更高版本；你还需要至少一个已经安装并登录的外部 AI CLI，或一个已经配置好密钥的 API 执行者。

安装 Codeck 命令

在 Codeck 仓库根目录安装依赖、构建并链接到系统命令。

npm install
npm run build
npm link
codeck doctor

在目标项目初始化

生成本项目的规则本，再填写项目说明与不能碰的禁区。

cd 你的项目目录
codeck init

# 然后填写：
.codeck/project.md
.codeck/constraints.md

先预览，再只读提问

第一次不要直接授权改代码，先完成一轮能追溯的只读交接。

codeck pick "让 Agy 检查当前 diff"

codeck ask antigravity \
  "检查当前 diff，按风险排序"

接入 Codex 后更自然

注册 MCP 服务后，你可以直接在 Codex 对话里说：“让 Kimi 梳理当前模块边界，只读分析。”Codex 继续当主持人，Codeck 在后台完成交接。

09 / 适用范围

谁会明显受益？

不是每个项目都需要多模型协作。判断标准很简单：你是否经常为了“再找一个 AI 看看”而重复搬运上下文。

很适合

  • 日常主力是 Codex，但已经订阅或登录了多个 AI CLI。
  • 项目较大，规则、架构和当前改动不适合每次手工复述。
  • 经常需要独立审查、方案对比、长代码阅读或专项顾问。
  • 希望每次 AI 交接都有记录，之后能搜索和复盘。

可能暂时不需要

  • 只使用一个 AI，从不切换工具。
  • 项目很小，复制两段文字已经足够。
  • 任何代码都不能发送给外部模型服务。
  • 只是想让 Codeck 免费提供模型额度——它不做这件事。

10 / 常见疑问

最后把容易误会的地方说透

Codeck 和直接复制粘贴有什么本质区别？

复制粘贴靠人记得“该带什么”；Codeck 把材料来源、长度控制、执行者权限、长任务续接和留档变成固定流程。项目越大、切换越多，这个差别越明显。

它会不会自己决定换成另一个模型？

在 Codex 的默认使用约定里，不会：你要先明确点名 Codeck 或某个外援。若你自己在终端主动运行 codeck auto，它才会按项目里的关键词规则和默认执行者选择。

Codeck 是“多模型共识系统”吗？

它提供把同一任务交给多个执行者的 compare 能力，但不同答案不等于共识。真正的工作仍是找出它们在哪些事实上一致、哪里冲突，再由主持者决定。

长任务超过宿主等待时间，会不会丢？

不会立刻丢。MCP 调用接近等待上限时可以先返回 runId，外部进程继续运行；之后用 wait_run 或 codeck wait 取回当前状态和最终结果。

历史记录保存在哪里？

默认保存在当前项目的 .codeck/ 目录里，优先使用本地 SQLite 数据库；环境不支持时会退回 JSON 文件。它不是云端团队知识库，除非你自己导出或同步。

这个项目最关键的设计选择是什么？

不是“自动选最强模型”，而是“Codex 始终当主持人，用户明确点名外援”。这样谁被调用、什么内容被发送、外援能做什么，都更容易说清楚。

THE WHOLE IDEA

让 AI 换人，别让项目失忆。

Codeck 把“找另一个模型看看”从一次临时复制粘贴，变成可控制、可续接、可追溯的正式交接。你仍然掌舵，Codex 仍然主持，外部模型只在被点名时进场。
